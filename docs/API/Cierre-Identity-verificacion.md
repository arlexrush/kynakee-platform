## Contratos y límites de verificación

**Progreso: 9/9 hitos (100 % del cierre funcional backend dev delimitado).** Evidencia automatizada y confirmaciones manuales del titular separadas en este documento, la guía Postman y la gobernanza. Este porcentaje no incluye frontend, operación productiva, renovación OAuth tras expiración, ensayo de restauración, transición legacy de claves, purga periódica operativa ni infraestructura de integración aplazada. No se afirma cobertura manual exhaustiva de cada caso negativo o carrera.

- Registro: validar formato de correo; crear propietario pendiente sin access/refresh tokens. La respuesta informa que es necesario verificar el buzón y no garantiza entrega ni existencia. Un token opaco de verificación se entrega solo por correo, nunca por la respuesta HTTP. No registrar tokens ni direcciones en diagnósticos de errores.
- Confirmar correo: validar propósito, usuario/tenant, expiración, estado y uso único dentro de la misma transacción que activa al propietario. No activar cuentas deshabilitadas por una confirmación antigua. La confirmación no inicia sesión automáticamente; el usuario pasa por login.
- Reenvío: respuesta genérica para no revelar si existe una dirección. Limitar frecuencia por cuenta y origen. Una nueva emisión invalida tokens anteriores de ese propósito mediante coordinación transaccional por usuario, sin duplicar correo al reintentar la misma operación.
- Recuperación: solo cuentas activas; token separado de 30 minutos, de un solo uso. El consumo cambia contraseña, rota CredentialVersion y revoca refresh y otros tokens de recuperación atómicamente. No activa cuentas pendientes/inactivas ni inicia sesión. Login/refresh se coordinan con reset mediante bloqueo de cuenta. La API verifica versión, usuario, tenant, membresía y rol actuales; el rechazo del JWT anterior está probado por HTTP. Sesiones legacy sin claim deben volver a iniciar sesión. Gateway valida firma; la API es el límite de vigencia.
- Invitaciones: conservar propósito y expiración de 24 h existentes. No admitir tokens de alta/recuperación en aceptación de invitación. El token recibido por correo prueba acceso al buzón invitado. Probar desde el worker real, no solo con el diagnóstico SMTP host.
- Ninguna consulta SMTP o DNS se considera prueba de existencia de un buzón. Formato inválido es error de validación; entrega fallida/no confirmada es advertencia o estado pendiente, sin enumeración pública de cuentas. No bloquear por errores DNS transitorios ni prometer validación de buzón inexistente.
- Correos verificación/recuperación: handoff durable cifrado y atómico con emisión del token y resultado HTTP; reclamación y efectos locales atómicos. SMTP puede duplicar tras aceptación y caída antes del commit: no prometer exactly-once. No añadir Outbox compartido ni otro behavior.
- Claves HTTP: registro y solicitudes de correo reintentables requieren coordinación por operación y fingerprint protegido; confirmaciones requieren consumo transaccional único. Especificar replay, retención, límites y protección de resultados antes de implementar endpoints nuevos, sin imponer la clave a cada consulta.

## Límites actuales confirmados

El registro implementado devuelve 202 y un acuse genérico sin sesión; un propietario nuevo queda PendingVerification y no puede iniciar sesión hasta confirmar el token recibido por correo. La verificación dura 24 h, la recuperación 30 min y la reemisión aplica una espera de un minuto por cuenta/propósito. Los correos de cuenta se encolan cifrados en la transacción. El titular confirmó su recepción y los recorridos manuales de verificación, recuperación, reenvío e invitación mediante Postman en dev, además de sesiones, perfiles, membresías y aislamiento. El detalle de estados comunicados se recoge en `Postman/README.md`, sin credenciales ni respuestas exportadas. API/Gateway fueron arrancados después de la migración y la colección se sustituyó por 28 solicitudes que cubren 18 endpoints Identity y salud.

Las tres migraciones Identity están aplicadas en dev; la actualización se probó además con datos sintéticos en PostgreSQL efímero. Las suites HTTP usan endpoints/pipeline/JWT reales en TestServer; su evidencia es distinta de la confirmación manual del titular. Los recorridos no acreditan renovación OAuth tras expiración, todas las carreras por ngrok, producción ni páginas frontend de verificación, recuperación o aceptación. El remitente genera enlaces con token hacia las URL web configuradas para verificación y recuperación; abrirlos no consume el token ni cambia la contraseña. Estos cambios no acreditan las páginas web ni el envío real de los nuevos enlaces.

**Evidencia previa del enlace de verificación:** en la versión anterior `SmtpAccountEmailSenderTests` ejecutó 14/14 con transporte controlado; las pruebas combinadas de remitentes ejecutaron 29/29. Tras activar Docker, Test Explorer ejecutó `AccountActionHttpTests`: 16/16 superadas con TestServer y PostgreSQL 17 efímero mediante `EnsureCreated`; estas pruebas obtienen el token del trabajo cifrado, no del enlace del correo. La API dev fue recreada con la URL local de verificación y respondió HTTP 200 en `/health`; Gateway alcanzó Identity. Esta evidencia anterior no verifica el enlace nuevo de recuperación, correos reales, frontend ni el recorrido completo.

**Evidencia del enlace de recuperación:** la solución compila y las pruebas de `SmtpAccountEmailSenderTests` y `SmtpInvitationEmailSenderTests` pasaron 41/41 con transporte controlado y cobertura recogida mediante `dotnet-coverage`. Comprueban URL de recuperación, escape del token y rechazo de configuraciones inseguras. Con Docker activo, `AccountActionHttpTests` y `AccountActionWorkflowTests` pasaron 39/39 con PostgreSQL efímero; las pruebas HTTP obtienen el token del trabajo cifrado, no del enlace del correo. No se han probado SMTP real, la página web ni el recorrido completo con el nuevo enlace.

No enviar automáticamente correos a destinatarios adicionales. Los recorridos reales de cuenta usarán buzones de prueba del titular y protegerán tokens/cachés fuera de logs y del repositorio. No aplicar migraciones de otros módulos ni cambiar producción/staging.
